# Findings: idle worker PDP-failure investigation

Status: two complementary root causes are now proven with high confidence, covering both observations in the incident report. Neither required a browser/stealth/fingerprint change, and none was made.

- **Why the exact ugly string is visible at all**: deployment/branch provenance (§1–§2). Proven directly from `git`.
- **Why PDP extraction genuinely fails almost instantly until restart**: a documented Chrome memory leak whose only mitigation is a nightly rolling restart the worker has zero visibility into, combined with a `PlaywrightRuntime` that never verifies a cached browser/context handle is still alive, combined with a deliberately-unretried fast-fail path for CDP-connect errors and a DOM-fallback path with no retry logic at all (§3). Proven at the code level from four independent research passes; not yet confirmed against a live incident timeline (§8).

This document reports on `docs/scraper implementation prompts/investigate_idle_worker_pdp_failure.md`. Two narrow, additive observability changes were made (§7); no scraping/browser/stealth behavior was touched.

## 1. The exact string: deployment provenance, not process staleness

`origin/main` — the branch actually built into the deployed Docker image (`.github/workflows/docker-publish.yml` → `deploy.yml` → `deploy.sh`) — **still contains** the code that raises the exact incident string as a Python exception and lets it flow into `pricing_reports.error_message`:

```
$ git show origin/main:worker/scraper/target_extractor.py | sed -n '640,650p'
            if fail_on_unusable:
                raise ValueError(
                    f"PDP individual listing extraction failed (payload + rendered DOM): {listing_url}"
                )
```

That `raise` was **removed on `no_pdp`** (the branch this workspace is on) in commit `1520680` ("refactor: Remove unused error handling in target spec extraction", 2026-07-25) — replaced with a degrade-to-warnings return, and locked in by `worker/tests/test_report_error_message_leak.py` (added later, `37d0292`, 2026-08-04). **`1520680` was never merged to `main`.**

`origin/main` and `no_pdp` diverged at `dd304e2` (2026-06-27). Since then `no_pdp` has accumulated **84 changed files, +17222/-2849 lines** in `worker/`, including entire subsystems `origin/main` does not have at all: `cdp_preflight.py`, the `playwright_runtime.py` resource-breaker/transactional-start/orphan-task-reaper rewrite, `browser_runtime.py`'s client pool, `scrape_trace`/`scrape_events` structured logging, `test_report_error_message_leak.py`, and ~40 other test files. **Production is running scraper code from before all of this — over 7 weeks of unmerged hardening work**, not a "stale process" in the sense the incident report assumed.

Independent confirmation this is live, not historical: `.github/workflows/daily-agent.yml` runs a Playwright E2E check against `https://airahost.com` every day at 00:00 UTC and commits whatever `error_message` it observes to `tests/<date>/agent_error_report.md`. `tests/2026-08-20/agent_error_report.md` (commit `704d52f`, today) exists only on `origin/main` and records this exact string against a real production report URL, generated fresh by that day's run — not a cached/stale UI value.

**This finding explains why the ugly internal string specifically is what shows up** — it does not by itself explain why extraction is actually failing. §3 covers that.

## 2. Why the error can appear without a matching claim log

Checked directly: `origin/main`'s `worker/main.py` **does** emit both `"[{report_id}] claimed (...)"` (`:2681`) and `"Claimed job {report_id} (attempt {attempts})"` (`:2733`) before calling `process_job()`, for the ordinary path — so an old revision alone does not explain a missing claim log for a *first-attempt* report.

Three real, code-confirmed mechanisms can still produce "error visible, no matching claim log":

- **Max-attempts short-circuit** (`worker/main.py`, `no_pdp:3007-3020`, `origin/main:2718+`): if `job.get("worker_attempts", 0) > MAX_ATTEMPTS`, the loop logs `"[{report_id}] claimed (...)"`, then immediately calls `fail_job(...)` with a fixed generic message and `continue`s — `"Claimed job ..."` and `process_job()` are **never reached**. Writes a *different*, non-PDP message, so it doesn't explain the exact string, but it's a genuine, provable case where the incident's own stated invariant ("both lines always precede `process_job`") is false by design.
- **Operator looking at a differently-shaped log.** `origin/main` lacks `scrape_trace`/`scrape_events` entirely (§1), so an operator expecting `no_pdp`-shaped structured events would find nothing to search for, not because the claim didn't happen.
- **Confirmed lane/environment mismatch between how anyone can reproduce locally and what actually runs in production** (new, from the deployment retry): `scripts/run-local-stack.ps1:222` **hardcodes** `WORKER_ENV=local; WORKER_LANE=nightly` for the one worker it starts. `deploy.sh`/`worker/Dockerfile` never set `WORKER_LANE`/`WORKER_ENV` at all, so the production container always runs on the code defaults `WORKER_ENV="production"`, `WORKER_LANE="interactive"` (`worker/main.py:76-77`). **No launch path in this repository ever produces a production `nightly`-lane worker, and no launch path ever produces a local `interactive`/`production`-lane worker.** Anyone who reproduces this locally via `run_local_stack.cmd` is, by construction, looking at a different lane/environment than the one that served the real incident — a concrete instance of "operator inspected the wrong lane/environment," not a hypothetical one.

## 3. Why extraction actually fails, fast, until restart — the mechanism

Four independent research passes (PDP-extraction-chain trace, Playwright/CDP runtime lifecycle ×2, deployment/launch-script audit) converged on one coherent, multi-source-corroborated chain. Each link below is confirmed by direct code reading, not inference.

**3a. Chrome is killed and relaunched out from under the worker on a schedule the worker cannot see.**
`scripts/restart_chrome_rolling.ps1` force-kills the `chrome.exe` process bound to each CDP port (`9222`, `9223`, `9224`) and relaunches it, one port at a time, with a persistent per-port profile. `docs/memeory_leak_bug.md:120-129` documents this as a **scheduled Windows Task Scheduler job (e.g. 3:00 AM daily)**, deployed specifically to mitigate a documented, unfixed Chrome/CDP memory leak ("Chrome's memory usage grows continuously... eventually hits its memory ceiling"). The worker process has no code path that is aware this happens.

**3b. Nothing in the worker ever verifies a cached browser/context handle is still alive.**
`PlaywrightRuntime.get_context()`/`get_browser()` (`playwright_runtime.py`) are bare `is not None` checks — confirmed across two independent research passes, no exceptions found. No liveness ping, no `browser.is_connected()` call, no `disconnected` listener, anywhere in `playwright_runtime.py`, `browser_runtime.py`, or `cdp_preflight.py`. `_select_context()` reuses `browser.contexts[0]` when one exists and marks it `owned=False`, so `reset()`/`stop()` never close it — only the Python-side driver/websocket is torn down on reset, never the underlying Chrome-side context. `ensure_started()` short-circuits to a no-op the instant `_started` is `True`, with no re-verification.

**3c. When a connection to a dead/frozen Chrome does fail, the failure is fast and deliberately not retried.**
`_get_listing_details_browser()` (`playwright_scraper.py:3588-3741`) classifies CDP-connect-shaped errors via `_is_cdp_connect_error()` (matching `"connect_over_cdp"`, `"retrieving websocket url"`, the literal devtools URL) and, on match, logs `"Browser PDP fast-fail on CDP connect error... (skip retry)"` and **breaks immediately on attempt 1** — explicitly skipping both the normal second attempt and `_reset_browser_connection_after_failure()` (`:3705-3736`). This is a deliberate, already-documented "no recovery" classification: `docs/fix_cdp_connection.md` independently describes this exact failure shape (Chrome freezing under host memory pressure → `Timeout 15000ms exceeded` on CDP connect) and states plainly it has **no recovery path**. Bounded only by the CDP connect timeout (15s) or runtime-start timeout (60s) — far faster than the normal 45s-per-attempt × 2-attempt budget.

**3d. The DOM-fallback path that runs immediately after has zero retry logic of its own.**
`target_extractor._extract_via_browser_dom()` (`:598-628`) and `_extract_target_spec_via_playwright_bridge()` (`:443-467`) are both bare `try/except Exception as exc: return None, [f"...failed: {exc}"]` — confirmed line-by-line: neither function's `except` block calls `_reset_browser_connection_after_failure`, `_runtime.reset()`, or retries in any way. Against the same degraded connection from 3b/3c, this fails just as fast, immediately behind the payload-path failure.

**Net effect**: on a worker that hasn't made a real CDP call since before Chrome was last force-restarted (3a) or since Chrome's memory footprint degraded its responsiveness, the *first* real report after that point hits a connection that either doesn't exist anymore or is unresponsive. Neither payload-path nor DOM-fallback-path retries or resets against it (3c, 3d) — so both halves of "(payload + rendered DOM)" fail within roughly one connect-timeout window, not the tens of seconds a genuine multi-method sequential attempt would take. This is a precise, code-level match for **both** of the incident's stated observations: implausibly fast failure, and full failure of every configured method.

**Why restart fixes it**: restarting the *worker* process forces a brand-new `PlaywrightRuntime` on next use, i.e. a fresh `connect_over_cdp()` attempt. If Chrome's own state has since recovered (rolling restart already ran, or host memory pressure cleared), a fresh connection attempt succeeds where a resurrected stale one wouldn't have. Separately, if the *worker* process itself had accumulated memory/handle pressure (the codebase already has a dedicated `_ResourceBreaker` for Windows spawn-exhaustion/WinError 1455, and `main.py`'s failure path has a special-cased friendly message for exactly this condition — evidence this general class of problem has been hit before), killing and restarting the worker process would relieve that side of the pressure even without Chrome itself changing. Both are consistent with "restart fixes it" without requiring the fix to be anything more than incidental timing relative to Chrome's own health.

## 4. Deployment/restart facts

`worker/Dockerfile`: `COPY . worker/` then `CMD ["python", "-m", "worker.main"]` — no build-time commit capture, no `.git` in the image. `deploy.sh` (identical on both branches): tags the image with the exact `GITHUB_SHA`, then `docker pull` → `docker stop`/`docker rm` → `docker run -d --restart unless-stopped ...`. Before this investigation the container never received `WORKER_VERSION`, so it could never identify its own deployed revision in its own logs (fixed in §7).

Two genuinely different things get called "restart" here:
1. **Redeploy** (merge to `main` → Docker Publish → Deploy Worker → full container replace): changes code *and* clears process state. Per §1, this *cannot* be what removed the raw-string leak, because the fix isn't on `main` — but it could coincidentally change extraction *behavior* if the new commit touched anything scraper-related.
2. **Plain restart** (`docker restart`, host reboot via `--restart unless-stopped`, or a manual container restart): same image/code, only in-process state clears — the exact mechanism §3 describes (a fresh `PlaywrightRuntime`).

Given §3 does not depend on which kind of restart occurred (a fresh connection attempt happens either way), this ambiguity no longer blocks the mechanism explanation — it would only matter for deciding whether a *specific historical* "restart" also happened to ship a code change.

Confirmed separately (deployment retry): production runs on a **Windows** host (`scripts/monitor_memory.ps1` and `docs/memeory_leak_bug.md` both reference the literal path `C:\Users\Aira\Desktop\airahost\...`), consistent with the GitHub Actions `deploy.yml` job's `runs-on: self-hosted` — the Docker container and the host-level Chrome/CDP processes it connects to over `CDP_URL` are colocated on the same Windows machine, not split across a cloud container host and a separate browser host.

## 6. Two more concrete gaps confirmed (not yet fixed)

- **`worker/core/scrape_events.py` is the real location of structured event logging** — the source investigation prompt's reference to `worker/scraper/scrape_events.py` is a stale/wrong path. Confirmed directly: it already provides a redacting, non-raising, JSONL-plus-human-readable-summary event sink (`worker/logs/worker.jsonl`, 20MB/5-backup rotation, `WORKER_EVENT_LOG_ENABLED`/`WORKER_EVENT_LOG_STDOUT`/`WORKER_EVENT_LOG_PATH` env overrides) with a real event vocabulary (`direct_http_*`, `playwright_started/captured_json/failed`, `circuit_*`, `retry_*`, `artifact_captured`, etc.) — much of the "reuse existing artifact/event infrastructure" the source prompt asks for already exists.
- **Still genuinely missing from that vocabulary**: no `claim_rpc_started`/`claim_rpc_returned`/`job_claimed` event, and no single terminal per-PDP-method event carrying `source/outcome/reason/duration` in one place (existing events are close but split across several call sites without a unifying per-attempt elapsed-time field on the failure branches — confirmed `_try_pdp_api_listing_details()` only computes `elapsed_ms` on its success path, not on any of its four exception branches). This is exactly items 2 and 4 of the source prompt's "Required observability changes" — not built here (see §8), but now precisely scoped.

## 7. What was changed (narrow, additive, evidence-justified)

Two changes, both purely additive (no scraping/browser/stealth logic touched):

1. **`worker/main.py`** — extracted `_log_worker_startup_identity()`, called at the top of `main()`, logging a short opaque `instance_id`, `host`, `pid`, `start_time_utc`, `executable`, `cwd`. Covered by `worker/tests/test_worker_startup_identity.py`.
2. **`deploy.sh`** — passes `-e "WORKER_VERSION=${GITHUB_SHA}"` into the container, so the already-logged, already-included-in-every-failure-`debug`-dict `WORKER_VERSION` field reflects the actual deployed commit instead of a static placeholder.

Verified: `pytest worker/tests/test_worker_startup_identity.py worker/tests/test_worker_logging_config.py -q` → 6 passed. `python -m unittest discover -s worker/tests` → 108 passed. Full `pytest worker/tests` → 913 passed, 3 skipped, 7 failed (all 7 pre-existing, in price-parsing/comp-coverage tests unrelated to anything touched here — confirmed by file path, none overlap `main.py`, `deploy.sh`, or the new test file).

## 8. What remains unproven

- **Live timing correlation for §3's mechanism.** The mechanism is proven at the code level from four convergent research passes, but no live incident timeline (real report row history, real worker logs, real Task-Scheduler run history for `restart_chrome_rolling.ps1`) was available to confirm a specific failure actually fell within a CDP-connect-timeout window or shortly after a scheduled Chrome restart. §6's missing instrumentation (per-PDP-method terminal event with elapsed time and reason code) is what would make the *next* recurrence provable rather than inferred.
- **Whether a `PlaywrightRuntime` lease/registry entry is ever held continuously across a multi-day idle gap**, vs. always released and rebuilt fresh per report (hypothesis 3, §5). Unresolved by every research pass so far — genuinely out of scope of the files read. Does not block §3's mechanism, which works either way, but would change how "idle for days" specifically maps to the failure window.
- **Whether the legacy 2-arg claim RPC has ever actually fired against the production Supabase project** (hypothesis 5) — requires confirming migration 012's applied state there, which this workspace cannot check.
- **The full opt-in bounded idle-soak harness and per-boundary elapsed-time instrumentation** (`job_created → claim → pdp_methods → extraction → fail → observed`) requested by the source prompt was not built — this investigation prioritized converging on root cause over building the harness, per the prompt's own preference for evidence over instrumentation-for-its-own-sake. Recommended as the concrete next engineering task if §3 needs live confirmation before code changes are made.

## 9. Recommended next steps (not executed — each requires an explicit decision)

1. **Merge `no_pdp` into `main` (or cherry-pick `1520680`) and redeploy.** Removes the exact leaking string (already tested), and brings production up to the same PDP-extraction robustness level (`cdp_preflight`, resource breaker, structured events) already present here — which would also make any future recurrence of §3's mechanism far easier to diagnose directly from production logs.
2. **Add a liveness check to `PlaywrightRuntime`, or a periodic keep-alive independent of the task-count-gated `_maybe_run_periodic_airbnb_auth_check`.** §3b/§3c/§3d together mean a report's very first real PDP attempt is what discovers a dead connection, with no retry once it does. Even a cheap `browser.is_connected()` check before use, or resetting the runtime proactively when `cdp_preflight` next runs, would very plausibly eliminate the fast-fail pattern without touching stealth/fingerprint behavior at all — this is squarely a reliability fix, not a detection-evasion one.
3. **Coordinate `restart_chrome_rolling.ps1`'s schedule with the worker**, e.g. by having it also signal/restart the worker container immediately after each Chrome restart, or by having the worker's periodic health check run frequently enough to catch a post-restart dead connection before a real report does.

Both #1 and #2 are independently justified by the evidence above; neither depends on the other being done first.
